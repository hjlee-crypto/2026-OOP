# [9~15주차] 객체지향프로그래밍 팀 프로젝트 안내

# 1. 프로젝트 개요

객체지향프로그래밍(OOP)의 핵심 원리를 적용하여 실제 동작하는 프로그램을 개발하는 팀 프로젝트입니다.

- **진행 기간:** 9~15주차 (15주차 최종 발표)
- **팀 구성:** 2~4명
- **개발 언어:** Java 또는 Kotlin
- **프로젝트 주제:** 제시된 4개 주제 또는 팀별 자유 주제
- **개발 방식:** 직접 코딩, 생성형 AI 활용, 바이브코딩 모두 허용
- **구현 형태:** 콘솔, GUI, 웹, 모바일 애플리케이션 등 자유 선택

프로젝트는 **은닉성(캡슐화), 상속성, 다형성, 추상성**을 실제 프로그램 설계에 적절하게 적용하고, 구현한 핵심 기능이 정상적으로 동작하도록 완성해야 합니다.

UI 디자인의 미적 완성도는 평가하지 않습니다.

# 2. 프로젝트 주제

다음 중 하나를 선택하거나 팀에서 자유롭게 주제를 정할 수 있습니다.

1. **도서관 도서 대출·반납 관리 시스템:** 도서 검색, 대출·반납, 연체료 계산
2. **은행 계좌 및 금융상품 관리 시스템:** 계좌 관리, 입출금, 이자 계산
3. **영화관 좌석 예약 및 요금 관리 시스템:** 영화 선택, 좌석 예약, 요금 계산
4. **쇼핑몰 상품·주문 관리 시스템:** 상품 관리, 장바구니, 주문·취소
5. **팀별 자유 주제:** 팀에서 기획한 프로그램

프로젝트 규모나 기능의 개수보다 객체지향 설계의 적절성과 핵심 기능의 완성도를 우선합니다.

# 3. 객체지향 필수 적용 사항

- **은닉성:** 객체의 상태를 보호하고 메소드를 통해 안전하게 관리
- **상속성:** 상위 클래스의 공통 속성과 기능을 하위 클래스에서 재사용
- **다형성:** 상위 클래스 또는 인터페이스 타입을 통해 서로 다른 객체의 동작 처리
- **추상성:** 추상 클래스 또는 인터페이스를 활용하여 공통 기능과 규약 설계

이와 함께 클래스·객체, 생성자, 메소드 오버라이딩, 컬렉션, 패키지 등 학습한 내용을 프로그램의 목적에 맞게 활용합니다.

**OOP 문법을 형식적으로 사용한 경우와 객체지향 원리를 실제 프로그램 구조에 적절하게 적용한 경우는 평가 점수에 차이가 있습니다.**

예를 들어 여러 클래스를 만들었더라도 주요 기능을 하나의 클래스에서 절차적으로 처리한다면 높은 평가를 받을 수 없습니다.

# 4. 생성형 AI 및 바이브코딩 활용

**생성형 AI를 활용한 전체 프로그램 개발(바이브코딩)을 허용하며, AI 활용 비율 자체는 감점 대상이 아닙니다.**

다만 생성형 AI를 어느 정도 활용했는지 명시해야 합니다.

### ① 생성형 AI 활용 수준 표시

다음 중 가장 가까운 수준을 선택합니다.

| 수준 | 생성형 AI 활용 정도 |
| --- | --- |
| 0단계 | 생성형 AI를 사용하지 않고 직접 개발 |
| 1단계 | 개념 이해, 오류 확인, 코드 설명 등에 활용 |
| 2단계 | 일부 클래스·메소드·기능 구현에 활용 |
| 3단계 | 주요 기능과 클래스 구조 생성에 적극 활용 |
| 4단계 | 바이브코딩 중심으로 프로그램 대부분 또는 전체 구현 |

활용 수준은 **평가 감점 기준이 아닌 개발 방식 확인을 위한 자료**입니다.

### ② 생성형 AI 활용 내역 작성

- 사용한 생성형 AI 도구
- 활용 수준(0~4단계)
- 주요 활용 내용(설계, 코드 생성, 오류 수정, 테스트 등)
- AI가 생성한 코드 중 팀에서 검토하거나 수정한 부분
- 팀에서 직접 결정한 객체지향 설계 내용

## 5. 코드 이해도 확인

바이브코딩으로 구현한 프로그램도 팀원들이 주요 코드의 동작과 객체지향 설계를 이해해야 합니다.

최종 발표에서는 다음 사항을 확인합니다.

- 주요 클래스와 메소드의 역할 설명
- 클래스 간 상속·인터페이스 관계 설명
- 은닉성·상속성·다형성·추상성을 적용한 이유 설명
- 주요 기능의 실행 흐름 설명
- 특정 코드의 변경 또는 오류 수정 방법 설명

**발표 중 교수자가 특정 클래스나 메소드에 대해 질문하거나 간단한 코드 수정 및 재실행을 요청할 수 있습니다.**

AI가 생성한 코드라도 팀원이 구조와 동작을 정확하게 설명하고 수정할 수 있다면 불이익이 없습니다.

## 8. 평가 방법

프로젝트는 **OOP 설계 및 적용, 기능 구현, 코드 이해도, 개발 과정 및 협업, 최종 발표**를 종합하여 100점 만점으로 평가합니다.

### ① 평가 원칙

- **객체지향 설계 및 적용(50점):** 은닉성·상속성·다형성·추상성의 실제 적용 여부와 객체 간 협력 구조를 평가합니다.
- **핵심 기능 구현(20점):** 계획한 기능의 정상 동작과 오류 처리 여부를 평가합니다.
- **코드 이해도(15점):** 주요 코드의 역할, 실행 흐름, 설계 이유 및 수정 능력을 확인합니다.
- **개발 과정 및 협업(10점):** 팀원별 역할, GitHub 개발 이력, 생성형 AI 활용 내역을 확인합니다.
- **최종 발표(5점):** 프로그램 시연과 발표의 명확성을 평가합니다.

### ② 평가 시 유의사항

- 객체지향 원리를 실제 프로그램 설계에 적절하게 적용했는지 중점 평가합니다.
- 무엇으로 개발을 했더라도 절차적 구조에 의존하면 OOP 관련 점수가 낮아집니다.
- 단순히 `extends`, `implements`, `private`, `abstract` 등의 문법을 사용한 것만으로 높은 점수를 받을 수 없습니다.
- 바이브코딩으로 전체 프로그램을 개발해도 감점하지 않습니다.
- 생성형 AI 활용 수준보다 코드 이해도와 설계·구현 완성도를 평가합니다.
- UI의 시각적 완성도는 평가하지 않습니다.
- 팀원별 개발 기여도와 코드 이해도는 GitHub 이력 및 발표 질의응답을 통해 확인합니다.

## 10. 최종 발표 시 코드 이해도 확인

최종 발표에서는 팀원별로 주요 코드의 이해도를 확인할 수 있습니다.

| 확인 영역 | 질문 예시 |
| --- | --- |
| 클래스 구조 | 이 클래스를 별도로 만든 이유는 무엇인가요? |
| 은닉성 | 이 필드를 private으로 선언한 이유는 무엇인가요? |
| 상속성 | 부모 클래스와 자식 클래스의 역할을 어떻게 구분했나요? |
| 다형성 | 부모 타입 또는 인터페이스 타입으로 객체를 처리하는 코드를 보여주세요. |
| 추상성 | 추상 클래스 또는 인터페이스를 사용한 이유는 무엇인가요? |
| 실행 흐름 | 특정 기능을 실행하면 어떤 메소드가 어떤 순서로 호출되나요? |
| 코드 수정 | 새로운 유형이나 기능을 추가하려면 어떤 클래스를 수정해야 하나요? |

필요한 경우 교수자가 간단한 코드 수정 및 재실행을 요청할 수 있습니다.

**최종 평가의 핵심은 프로그램의 외형이나 코드 분량이 아니라, 객체지향 원리를 실제 설계에 적절하게 적용했는지, 기능이 정상적으로 동작하는지, 팀원들이 작성된 코드를 이해하고 수정할 수 있는지입니다.**
